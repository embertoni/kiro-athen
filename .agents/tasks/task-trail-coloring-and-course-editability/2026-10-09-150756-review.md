# Trail coloring/centering and draft-vs-published course editability gating

Two independent requirements land in one branch. The dashboard trail now paints its connectors with the current module's color and keeps the selected node centered horizontally (replacing the old `scrollIntoView` left-snap), with the centering math pulled into a pure, unit-tested helper. Separately, a data-layer gating rule makes draft courses fully editable and freezes a published course's pre-existing content while still allowing brand-new modules — enforced server-side by a new RLS migration (`0019`), mirrored by a `saveCourseTree` guard and defensive UI affordances in the create page. The two features share no code and can be judged independently.

Watch for: new modules added to a *published* course are inserted with `position: mIndex` computed over the full draft list, which overlaps the positions of the retained pre-existing modules (**likely** — no unique constraint, so no error, but trail ordering is corrupted). The published→draft "unpublish" path is asymmetric: RLS would re-permit full edits, but `saveCourseTree` gates its destructive rebuild on the pre-save status and would therefore *not* rebuild children (**possible** — unreachable from today's create-only UI). The RLS logic cannot be executed in this sandbox (no live Supabase); it was reviewed structurally only.

**Verdict**: NEEDS_CHANGES

## High-level view

The centering is a pure function `computeCenterScrollLeft` (node center minus half the container, clamped to `[0, max(0, maxScrollLeft)]`) driven by an effect keyed on `[focusedModuleId, trail]`, writing to the same `trailRef` container the drag/wheel handlers mutate — so programmatic centering and manual drag don't fight over two different scrollers. Current-module color resolution flows through `resolveModuleColor(color ?? var(--brand-purple))` and is pushed into CSS custom props; a separate effect defaults `focusedModuleId` to the first module so the trail always has a color. Drag/wheel scrolling is untouched.

The editability rule has a server authority (migration `0019`) and two client mirrors. `0019` adds a nullable `courses.published_at`, a `BEFORE INSERT OR UPDATE` trigger that stamps it on first publish only, and replaces the `0011` `FOR ALL` write policies with granular INSERT/UPDATE/DELETE policies. The discriminator for "new vs pre-existing" content under a published course is `module.created_at > course.published_at`. UPDATE/DELETE are allowed only while the course is `draft`; INSERT of lessons/questions is allowed under a draft course or under a *new* module of a published course. `is_admin()` overrides throughout, and the `0011` `_select` policies are left alone.

`saveCourseTree` reads the pre-save course status and only runs the destructive delete-all-modules-then-reinsert when the existing course was a draft (so draft→publish still rebuilds, but editing an already-published course only inserts id-less modules). The create page computes `isExistingContentLocked` and hides remove buttons / disables inputs for persisted content of a published course while keeping "add module" and "publish" live. The gating is currently defensive: the `/create` route never hydrates an existing course, so `courseId`/`courseStatus` sit at create defaults and the locked path is not yet reachable from the UI.

The known gaps are a position-numbering bug when appending modules to a published course, and the unaddressed unpublish asymmetry between RLS and `saveCourseTree`.

### Centering math and the single-scroller invariant

`computeCenterScrollLeft` places the node center at the container center (`nodeOffsetLeft + nodeWidth/2 - containerWidth/2`) and clamps to `[0, max(0, maxScrollLeft)]`. The `Math.max(0, maxScrollLeft)` guard matters: when content fits the container `scrollWidth - clientWidth` is negative, and without it the clamp would collapse to a negative upper bound. Covered by five unit tests (mid-range, both clamp ends, wider nodes, negative `maxScrollLeft`); math **confirmed** correct.

The centering effect reads `node.offsetLeft`, which is relative to the nearest positioned ancestor. This is correct only if `trailRef`'s element is itself the offset parent of `.dash__module`. `.dash__track` gained `position: relative` in this diff, making it the offset parent — but `trailRef` must point at that same `.dash__track` element for `offsetLeft` and `scrollLeft`/`clientWidth` to share an origin. If `trailRef` is attached to a wrapper around `.dash__track`, the measurement is off by the wrapper's padding/border. Worth confirming `trailRef` is on `.dash__track` (**possible** — the ref attachment is outside the shown hunks).

Both the drag handlers and the programmatic `scrollTo` write to the same `trailRef` container, so there is one scroller and centering never diverges from manual drag; `useHorizontalDragScroll` is unchanged, so wheel/drag is not regressed.

### RLS gating: new-vs-existing discriminator and the policy split

The `0011` `FOR ALL` `modules_write`/`lessons_write`/`questions_write` policies are replaced by granular INSERT/UPDATE/DELETE policies; the `_select` policies are untouched. UPDATE and DELETE on all three tables require the owning course to be `draft` (or admin), freezing a published course's content against modification and removal. INSERT carries the new-vs-existing rule: a module insert is allowed under a draft *or* published course; a lesson/question insert is allowed under a draft course, or under a published course only when the owning module satisfies `c.published_at is null or m.created_at > c.published_at`. The `created_at > published_at` discriminator correctly distinguishes modules added after publication from those that predate it.

```
            is_admin ──────────────────────────────────► allow (any op)
  module INSERT: creator && course.status in (draft,published) ► allow
  lesson/question INSERT:
      creator && (draft)                                       ► allow
      creator && published && (published_at IS NULL
                                 OR module.created_at > published_at) ► allow
  UPDATE/DELETE (all three): creator && status='draft'         ► allow
```

The trigger guards the `old` reference with `tg_op = 'INSERT' or old.status is distinct from 'published'`, so it does not evaluate `OLD` on INSERT. The backfill is idempotent (`status='published' and published_at is null`), and every policy is `drop ... if exists` before create, so the migration is re-runnable. SQL reviewed structurally only — **no live Supabase in the sandbox**, so RLS behavior was not executed.

The trigger never clears `published_at`. For a one-way draft→published lifecycle that preserves the publication boundary, but a published→draft→published cycle keeps the original `published_at`, so any module created during the draft-again window has `created_at < published_at` and would be treated as pre-existing/immutable on re-publish, even though the creator added it while editing freely. If unpublish-and-edit is a real flow, `published_at` should be cleared on unpublish (or advanced on each re-publish) (**likely** — follows from the trigger logic, contingent on unpublish being supported).

### `saveCourseTree` guard and the unpublish asymmetry

The guard reads the pre-save status before the update, so `allowReplaceChildren` reflects the on-disk state, not the target status: draft→publish rebuilds; editing an already-published course skips the destructive delete and inserts only id-less modules. That mirrors the RLS rule for the forward lifecycle and avoids issuing deletes RLS would reject.

The asymmetry is the published→draft case. If an edit flow ever submits a draft save for a course whose on-disk status is `published`, `allowReplaceChildren` is `false`, so children are not rebuilt — but RLS, seeing the row now at `status='draft'`, would permit a full rebuild. The data layer is stricter than the server here, which is safe (no rejected writes) but surprising: unpublishing then editing would silently not persist edits to pre-existing content. Not reachable from today's create-only UI, so this is **possible**-confidence and forward-looking; it should be resolved before any edit/unpublish entry point ships.

### New-module position numbering under a published course

In the published-course branch the loop skips `moduleDraft.id`-bearing modules but still inserts brand-new ones with `position: mIndex`, where `mIndex` is the index in the full `draft.modules` list. Pre-existing modules retain their stored positions (they are not touched), so a new module appended after, say, three retained modules may be inserted at `position: 3` while a retained module already occupies `position: 3`. There is only an index on `(course_id, position)`, no unique constraint, so the insert succeeds silently and the trail ends up with duplicate/overlapping positions, corrupting ordering. The fix is to derive the new module's position from the retained set (count of pre-existing modules, or `max(existing position) + 1`) rather than the draft index (**likely** — logic is clear from the diff; the exact ordering impact depends on how the trail sorts equal positions, which was not traced).

### UI affordances vs the data-layer rule

The affordances match the RLS rule: `isExistingContentLocked` (combined with per-entity `isPersisted`) hides remove buttons, disables inputs/Select, and wraps `QuestionConfigEditor` read-only for persisted content of a published course, while "+ Adicionar módulo"/"Publicar" and add-lesson/add-question under unlocked modules stay live — i.e. no UPDATE/DELETE of existing content, additions still allowed. The `QuestionConfigEditor` lock is `pointer-events: none` + `aria-disabled` rather than a real disabled control, so it blocks interaction but not programmatic state changes; it leans on the server policy as the real enforcement.

The gating is defensive, not yet active: `courseId` and `courseStatus` are `useState` values fixed at `undefined`/`'draft'` with no setter wired, and the `/create` route never hydrates an existing course. So `contentLocked` is always `false` in the shipping UI, and the lock paths are exercised only by the helper unit tests. That is a reasonable forward-looking posture, but it means the UI↔RLS correspondence for the locked case is unverified end-to-end — only the pure helper is tested. **Not tested:** the locked-rendering branches of `CreateCoursePage` (no component test hydrates a published existing course), and the `saveCourseTree` published-course insert-only path (no test drives the DB-dependent branch). Both are DB/UI-integration seams that the pure-helper tests do not reach.

### Types regeneration

No client query selects `published_at`, so typecheck is clean today. Latent: once an edit flow or query references the column, the generated `database.ts` must be regenerated (`supabase gen types`) or the reference won't type-check.
