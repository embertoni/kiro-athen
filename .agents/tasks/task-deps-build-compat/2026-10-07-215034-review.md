# Supabase-js lockfile float, type-compat shim, and Vercel SPA rewrite (v1)

Regenerating `package-lock.json` on an open-internet environment floated `@supabase/supabase-js` from the previously-pinned resolution up to 2.117.3 (the `^2.45.0` range in `package.json` is unchanged). That version bundles a newer postgrest-js whose `GenericTable` constraint requires every table `Row`/`Insert`/`Update` to be assignable to `Record<string, unknown>`; the hand-generated `src/types/database.ts` declares each `Row` as a bare `interface`, which has no implicit index signature and fails that constraint, collapsing the typed client's schema to `never` and producing ~80 build errors. The fix leaves the generated file untouched and instead introduces a type-level normalization shim (`NormalizeDatabase`) wired into `createClient`, tightens the admin CRUD's dynamic-table casts into a single documented boundary, and adds `@types/node`, a `*.tsbuildinfo` ignore, and a `vercel.json` SPA rewrite. The change is type-level and config only — no runtime values are altered.

Watch for: the `NormalizeDatabase` shim normalizes only `Row`, not `Insert`/`Update` (confirmed sound — `Insert`/`Update` are already mapped-type-based via `Opt`/`Omit` and satisfy the constraint, so this is correctly scoped, not a gap). The lockfile silently advances supabase-js across ~70 minor versions (confirmed), which is a real supply-chain/behavior surface even though types and tests pass. The CRUD boundary cast widens write payloads to `Record<string, unknown>` and leans entirely on server-side RLS for safety (confirmed, by design).

**Verdict**: APPROVED

## High-level view

The root cause is correctly identified: a bare `interface` lacks the implicit index signature that `Record<string, unknown>` requires, which postgrest-js now enforces, collapsing the schema to `never`. `NormalizeDatabase` rewrites every table/view `Row` through a homomorphic mapped type to grant that signature without editing the generated source. It normalizes only `Row` — `Insert`/`Update` are already mapped-type-based (`Opt`=`Omit`&`Partial`) and pass the constraint — so the scope is minimal, not a gap.

The admin CRUD can't resolve a per-table row type because it picks its table at runtime, so the diff confines the previously-scattered `as unknown` casts into one `CrudQueryClient` interface and a single `crudClient` cast. The widened `CrudRow` (`Record<string, unknown>`) payloads mean TypeScript no longer guards what columns are written on admin update/delete; safety rests entirely on `is_admin` RLS. Acceptable for a generic admin tool, but a genuine narrowing of compile-time safety on write paths.

The courses comment-join cast changes from a direct `as` to `as unknown as` to match the two sibling joins (`courseJoined`, `moduleRows`) that already double-cast. The runtime expression is unchanged.

The lockfile is the largest and least-reviewable part: ~5200 inserted lines, with supabase-js advancing from a 2.45-era resolution to 2.117.3. Build, typecheck, lint, and 97 tests pass, but tests exercise app logic, not the SDK's wire behavior, so a minor-version behavior change in the SDK would not necessarily surface here.

## The `never` collapse and why a mapped type fixes it

postgrest-js's schema resolution requires each relation's `Row` to extend `Record<string, unknown>`. A TypeScript `interface` does not get an implicit index signature (only `type` aliases over object literals and mapped types do), so `interface ProfileRow { id: string; ... }` is not assignable to `Record<string, unknown>`. When any relation fails the `GenericSchema` constraint, the client's `Schema` parameter resolves to `never`, and every `.from(table)` chain downstream resolves against `never` — hence the "Property does not exist on type 'never'" / "not assignable to parameter of type 'never'" wall.

`NormalizeRow<Row> = { [K in keyof Row]: Row[K] }` is a homomorphic mapped type over the same keys; the result is structurally identical to the input but, being a mapped type, carries the implicit index signature that satisfies `Record<string, unknown>`. `NormalizeRelations` rewrites only the `Row` member of each entry and preserves `Insert`/`Update`/`Relationships` via `Omit<..., 'Row'> & { Row: ... }`. `NormalizeSchema` restricts the rewrite to the `Tables` and `Views` keys and passes everything else through, and `NormalizeDatabase` maps it across every schema. The transform is identity at the value level, so `createClient<SupabaseDatabase>` produces the same runtime client; only the compile-time schema resolution changes.

Normalizing `Row` but not `Insert`/`Update` looks like an omission but isn't: in the generated file `Insert`/`Update` come from `Opt<Row, K> = Omit<Row, K> & Partial<Pick<Row, K>>`, and `Omit`/`Partial` are mapped types whose outputs already satisfy the `Record<string, unknown>` constraint. The bare `interface` `Row` was the only member that failed it, and `tsc --noEmit` passing end-to-end confirms the narrower normalization is sufficient.

## CRUD dynamic-table boundary

The admin CRUD selects its table from `CrudEntityConfig.table` at runtime, so there is no single `Row`/`Insert`/`Update` the typed client can bind to — the typed `.from(cfg.table)` would resolve to a union the subsequent `.select`/`.update`/`.delete` can't reconcile, which is what drove the prior scattered `as unknown` casts. The diff replaces those with one `CrudQueryClient` interface describing exactly the three generic chains the CRUD uses, and a single `const crudClient = supabase as unknown as CrudQueryClient`. Typing `table` as `keyof Database['public']['Tables']` (`CrudTable`) instead of `string` is a real improvement: the three config entries (`profiles`, `courses`, `rooms`) are now checked against actual table names.

The cost is that `update(values: CrudRow)` and the select result are `Record<string, unknown>`, so writes are no longer column-checked at compile time. The boundary comment is explicit that `is_admin` RLS is authoritative, which is the right framing for a generic admin editor — but it does mean a typo in `editableKeys` or a wrong column name won't be caught by the compiler and will fail (or silently no-op) at the server. This is a reasonable, well-contained trade; flagging it so RLS coverage is treated as the actual guard rather than an afterthought.

Adjacent to the touched code: `coerceValue` maps `'true'`/`'false'` to booleans and returns every other value as a raw string. Numeric or date columns edited through the CRUD are therefore sent as strings and depend on PostgREST/Postgres coercion. This is pre-existing (not introduced by this commit) and only noted because the surrounding types changed; not a blocker.

## Courses comment-join cast alignment

`recentComments` builds from `commentsRes.data ?? []`, the result of a `comments` select with an embedded `author:profiles!...` join. Under the normalized client the join result's shape no longer directly overlaps `CommentRow & { author: ... }`, so the direct `as CourseDetail['recentComments']` cast stops compiling and becomes `as unknown as`. That now matches the two sibling joins in the same function — `courseJoined` and `moduleRows` — which already route through `as unknown as`. The runtime expression (`commentsRes.data ?? []`) is byte-for-byte unchanged; this is purely making the comment cast consistent with how the other joins in the same query are already handled. No runtime behavior change.

## Not tested

No new tests accompany this change, which is appropriate — the fix is type-level and config, and the 97 existing tests all pass. What the test suite does not cover, and cannot: the supabase-js version jump's runtime/wire behavior (auth session persistence, query serialization against a live PostgREST), and the CRUD write paths now that payloads are untyped. A manual smoke test of login/session and one admin CRUD edit against a real backend would close the gap the type-only verification leaves open.
