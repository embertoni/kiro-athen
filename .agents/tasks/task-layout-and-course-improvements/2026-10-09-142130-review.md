# Sidebar layout overhaul, Duolingo dashboard, and course/XP fixes (v1)

Four commits deliver the six requested changes: a self-enroll path for own private courses (plus RLS relaxation), creator-name catalog search, numeric level display, an anti-regrind XP rule in `finalize_attempt`, a full sidebar/dashboard layout overhaul with a light/dark theme toggle, and a profile identity-block rework. Behaviorally the change set matches the spec closely: the sidebar order and labels are exact, the dashboard honors every sub-requirement (horizontal draggable trail, module carousel, top-down panel split by Cursos/Salas, notice board), and the two SQL migrations are logically sound. The dashboard trail/locking hooks (`useCourseTrail`, `useDashboardOverview`) are unchanged from `main`, so trail correctness is out of scope here. Typecheck is clean, lint has 0 errors (6 pre-existing warnings), 112 tests pass, build emits `dist/`.

Watch for: the catalog creator-name search caps creator matches at 100, so courses by a matching creator beyond that cap silently won't surface (likely); the room ranking query fires even when PAC visibility hides the ranking (possible, cosmetic); "missões diárias globais" is a client-derived display with no backend, which is a deliberate, documented trade-off (confirmed). No live Supabase in the sandbox, so the two migrations are judged on logic, not execution.

**Verdict**: APPROVED

## High-level view

The enrollment change is split cleanly across layers: migration 0017 relaxes the `enrollments_insert_own` RLS policy to also permit `creator_id = auth.uid()`, and the catalog "Criados por mim" tab wires an existing `useEnroll` into a Matricular action. The policy change is minimal and mirrors a boundary `finalize_attempt` already enforced, so the two paths now agree.

Creator-name search is done server-side without a schema change: the catalog resolves matching creator ids from `profiles` and folds `creator_id.in.(...)` into the existing `.or()` on courses, because PostgREST can't OR across the embedded `creator` relation in one filter. The creator pre-query is capped at 100 rows.

The anti-regrind rule lives entirely in `finalize_attempt`: it keeps the 0010 body and adds a single check inside the grading loop that zeroes an answer's XP when the same user already answered that question correctly in a different, already-finalized attempt. Correctness (`is_correct`, `correct_count`) stays truthful; only `xp_earned` and the summed attempt XP are suppressed, and because the sum is accumulated before the course/room split, both contexts are covered.

The layout overhaul removes the top bar and builds one persistent sidebar whose order and labels match the spec exactly (including the plural "Cadernos" label on the `/notebook` route and the admin CRUD link appended after Configurações). The theme toggle sits above a profile footer; theme state is persisted and falls back to OS preference. The dashboard is rebuilt around a trail layer behind overlay UI, with a Cursos/Salas mode selector that swaps both the trail and the top-down panel contents, a module carousel, and a Salas-only notice board.

The profile rework moves level/xp/streak inline into the identity block, turns Cursos/Amigos into navigating buttons that still show counts, and pins up-to-3 featured medals into the identity block while leaving them unhighlighted in the full medal list — exactly the "move, don't highlight-in-list" behavior the spec asks for.

<summary>Issues (3)</summary>

1. **Creator-search 100-cap** — the `profiles` pre-query is `.limit(100)`; when more than 100 creators match the term, courses by the overflow creators won't appear in results. Consider raising/removing the cap or documenting it as acceptable.
2. **Room ranking fetches when hidden** — `RoomRanking` calls `useRoomMembers(roomId, true)` unconditionally, so the roster is fetched even when `pac_visibility` is `educator_only` and the ranking is not rendered. Gate the query's `enabled` on `rankingVisible` to avoid the wasted request.
3. **Global daily missions are display-only** — "missões diárias globais" is derived client-side from `last_study_date`/`streak_count` with no backend table and grants no XP. Deliberate and documented, but confirm the product accepts a non-persistent approximation.

### Self-enroll in an own private course (item 1)

Migration 0017 recreates `enrollments_insert_own` so the `with check` admits either the existing public+published path or `c.creator_id = auth.uid()`, while keeping `user_id = auth.uid()`. This aligns the explicit enrollment path with the boundary `finalize_attempt` (0010) already applied, which credited a creator's own course regardless, so the two paths no longer disagree. The "Criados por mim" cards route through the existing `useEnroll` mutation. Live RLS behavior can't be exercised in the sandbox; flag for verification against a live DB, though the predicate is correct on its merits.

### Creator-name catalog search (item 2)

PostgREST can't express an OR across the embedded `creator:profiles` relation inside a single `.or()`, so `useCatalog` first queries `profiles` for ids whose `display_name`/`username` match the term, then folds `creator_id.in.(...)` into the same courses `.or()`. The folded ids are UUIDs from DB rows, so that interpolation is safe.

The new gap is the `.limit(100)` on the creator pre-query (confirmed): if a term matches more than 100 creators, courses authored by the overflow won't be folded in, so results are silently incomplete at the tail. The raw term is still interpolated into the `ilike` filters, but that pattern is unchanged from `main`, so any breakage from commas/parens in the term is pre-existing and out of scope.

### Numeric level (item 3)

Both display sites drop the `L` prefix: `DashboardPage` (via the profile identity rework) and `GlobalRankingPage` now render `Nível {level}` instead of `Nível L{level}`. Confirmed in the diff.

### Anti-regrind XP in finalize_attempt (item 4)

Migration 0018 preserves the 0010 body and inserts one check in the grading loop: after `grade_answer` yields `(is_correct, xp)`, an `exists` subquery looks for the same `question_id` answered `is_correct = true` in a different attempt (`prev.attempt_id <> p_attempt_id`) belonging to the same user whose attempt is already finalized (`pa.finished_at is not null`). When true, `v_award_xp` is forced to 0.

```sql
v_already_correct := exists (
  select 1 from public.answers prev
    join public.attempts pa on pa.id = prev.attempt_id
   where prev.question_id = v_ans.question_id
     and prev.attempt_id <> p_attempt_id
     and prev.is_correct = true
     and pa.user_id = v_attempt.user_id
     and pa.finished_at is not null
);
```

Two properties make this correct. The current attempt can't suppress its own XP: it's excluded both by `attempt_id <> p_attempt_id` and by its still-null `finished_at` (the attempt's `finished_at` is set after the loop). And the suppression reaches both award paths because `v_total_xp` accumulates the zeroed value before the course/room branch, so neither `profiles.xp_global` (course) nor `room_members.xp_internal` (room) gains XP for an already-correct question, while `is_correct`/`correct_count` stay truthful. The idempotency guard (`v_already_final`) still fences the one-time side effects. Judged on logic only — no live DB to execute against.

### Sidebar order, labels, and the removed top bar (item 5, layout)

`NAV_ITEMS` is Painel, Catálogo, Salas, Ranking, Amigos, Cadernos, Notificações, Configurações, with the admin CRUD link appended last so it never perturbs the required order; all eight routes exist in `App.tsx`. The "Cadernos" label is intentionally plural over the `/notebook` route. The Notificações item carries an unread badge driven by the polled `useUnreadCount` hook that previously backed the top-bar bell. The theme toggle sits above the profile footer (banner, avatar, name, streak → `/profile`, plus logout), and the sidebar is mounted inside the shared `AppShell` outlet so it is constant across authenticated pages — all matching the spec. Theme state persists to `localStorage` and falls back to `prefers-color-scheme`.

### Dashboard trail and overlay UI (item 5, dashboard)

The trail layer sits behind the overlay controls, with square module nodes and circle lesson buttons; lesson state comes straight from `useCourseTrail` (unchanged from `main`, so the locking rule itself is out of scope). `useHorizontalDragScroll` only hijacks movement past a 4px threshold, so lesson clicks still register through the drag handler. The top-left Cursos/Salas selector swaps both the active trail and the top-down panel contents: Cursos shows `FriendsCourseRanking` by PAC plus the derived daily missions; Salas shows the room ranking, room missions, and the bottom-right notice board (`useAnnouncements`). In Salas mode the trail follows `selectedRoom.room.course_id`.

`RoomRanking` gates visibility with `visibility === 'members' || visibility === 'public'`, matching the existing `RoomDetailPage` rule so `educator_only` rooms correctly hide the roster from the learner-facing panel. One possible refinement: `useRoomMembers(roomId, true)` is called unconditionally, so the fetch runs even when the ranking is hidden — RLS still protects the data, but gating the query's `enabled` on `rankingVisible` would avoid the wasted request.

The "missões diárias globais" requirement is implemented as `deriveDailyMissions`, a pure function computing two display-only goals ("estude uma aula hoje", "mantenha a sequência") from `last_study_date` and `streak_count`. There is no backend global-missions table, so these grant no XP and never write back — a deliberate, documented trade-off (confirmed in `helpers.ts` and FEAT-004). Worth a product confirmation that a non-persistent approximation is acceptable.

### Profile identity block and featured medals (item 6)

Level, XP, and streak moved to inline stats inside the identity block. Cursos and Amigos became buttons that show the count and navigate to `/catalog` and `/friends`. Featured medals (`award.featured`) are pinned into the identity block as highlighted chips and removed from the `MedalsShowcase` featured row, so the full list now renders every medal unhighlighted — matching the spec's "move into the main block, don't highlight in the list". The "Destacar medalhas" chooser still caps selection at 3 (`prev.length >= 3`).

### Test coverage

New unit tests cover the pure seams: `deriveDailyMissions` (done/not-done and streak phrasing), `resolveInitialTheme`/`nextTheme`, and the two creator-name catalog predicate cases. Not tested (and not testable in-sandbox): the two SQL migrations (no live Supabase), the RLS policy behavior, the drag-scroll pointer interactions, and the dashboard overlay rendering. The SQL and RLS logic should be verified against a live database before relying on it in production.

### Bundled scope

`theme.css` grows substantially but only to add the dark palette and dashboard/sidebar styles, and `src/types/database.ts` is untouched (new query shapes rely on boundary casts, consistent with its generated status). No unrelated changes bundled in.
